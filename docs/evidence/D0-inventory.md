## A3. RLS on `sessions` (latest effective per migrations; live DB UNKNOWN)

RLS enabled: 20251012020423_f00f2350...:53. Default privileges for `authenticated`/`service_role` were re-granted wholesale by 20260712023825_7ddf10d6...:6-7 (`GRANT SELECT, INSERT, UPDATE, DELETE ON public.%I TO authenticated`), so table GRANTs do not limit direct writes; only RLS does. Column-level grants/revokes on sessions: none found by grep.

1. **"Admins can manage all sessions"** - `FOR ALL USING (public.has_role(auth.uid(), 'admin'))` - 20251012023454_6adfb949...:146-147 (replaced the get_user_role version at 20251012020423:69-71). No WITH CHECK -> USING applies. => an admin session JWT may INSERT/UPDATE/DELETE any session directly through PostgREST, bypassing every edge-function guard (S15-S20 do exactly this).
2. **"Teachers can update their sessions"** - `FOR UPDATE USING (teacher_id IN (SELECT t.id FROM teachers t WHERE t.user_id = auth.uid()) AND status = 'Scheduled')` - 20251012020423:79-86. Never dropped (grep over supabase/migrations and drizzle). No WITH CHECK, so Postgres applies the USING expression to the new row too: a teacher can edit date/start_time/end_time/rate_override_vnd/notes of their own Scheduled lessons but cannot set status to Canceled or Held (new row must still be 'Scheduled') nor reassign to another teacher. A teacher CAN move their own Scheduled lesson to another date/time with no admin involvement and no audit reason (audit_sessions trigger still logs). Which columns a teacher may touch is not limited (no column grants found).
3. SELECT: "Teachers can view their sessions" (20251012020423:73-77) and "Enrolled or teaching users view sessions" (admin / is_teacher_of_class / is_student_enrolled_in_class) 20260711235255:14-21 (replaced "Authenticated users can view sessions"; "Everyone can view scheduled sessions" dropped 20251015032902:15).
4. No INSERT/DELETE policy for non-admins. Students/parents have no write policy.

Consequence: edge-function guards in manage-session/bulk-cancel-sessions are advisory for admins: the admin client can cancel/delete directly (S18 is the existing example) and only the DB triggers (S12-S14) and audit trigger remain. Neither blocks a cancel.

## B. Known gaps - confirmed or refuted

(i) **manage-session `cancel` blocks only status 'Held' with a past date - CONFIRMED.** manage-session/index.ts:126 `if (session?.status === 'Held' && sessionDate < now)`. Past Scheduled lessons that were actually taught (not yet flipped Held, e.g. register not marked) cancel freely; reason not mandatory (l.120, no check). Additional: a lesson already Canceled is not rejected (idempotent overwrite of canceled_by/at). Also the UI CancelSessionDialog defaults the reason to "No reason provided" (CancelSessionDialog.tsx:36).

(ii) **`force-cancel` and `change-status` have no evidence check; force-cancel has a canned reason - CONFIRMED.** force-cancel: index.ts:158-190, reason `reason || 'Admin force-canceled (correction)'` (l.164). change-status l.192-236: only `['Scheduled','Held','Canceled']` check (l.195); reason default `'Admin status change'` (l.210). SessionActionsModal.tsx:66-68 picks force-cancel automatically when `isPastHeld`. change-status in the UI requires a reason (SessionActionsModal.tsx handleChangeStatus: `if (!newStatus || !reason)`), but the server does not.

(iii) **bulk-cancel-sessions has an optional reason and an `include_held` switch - CONFIRMED.** bulk-cancel-sessions/index.ts:15 `reason: z.string().max(500).optional()`, :16 `include_held: z.boolean().optional()`, :96-99 filter, :124 default reason. The UI sends a generated reason and `include_held: includeHeld` (BulkSessionDelete.tsx:80-91). Plus: all filters optional and `today` unused (l.92), so any past Scheduled session is cancelled.

(iv) **Guards live in edge functions, so a direct write under RLS bypasses them - CONFIRMED for admin.** Policy 1 above (FOR ALL, admin). Concrete existing bypasses: SessionActionsModal.tsx:135 (hard delete), EditSessionModal.tsx:123 (times), GlobalCalendar.tsx:191 (date/time). Teacher: cannot cancel/Held directly (policy 2) but can move own Scheduled lessons. REFUTED for the "teacher cancels directly" variant (policy 2 USING/CHECK). Live-DB drift is UNKNOWN.

Additional gaps found (not in the brief):
- (v) manage-session `delete` (l.315-333) and the client hard delete (S18) have no Held/past guard at all, and cascade-delete attendance (20251012062405:4).
- (vi) Un-cancel (S1/S4) is unguarded and un-refreshed; attendance stays Excused (S13 fires only into Canceled).
- (vii) auto-mark-attendance creates marked_by NULL 'Present' rows for every enrolled student of tonight's Scheduled/Held lessons (index.ts:99-107), so "attendance exists" is NOT proof a lesson was held; same for repair-attendance (marked_by null, l.100) and the AFTER INSERT seed trigger (20251012065759; seeds attendance on session creation).
- (viii) watch-sibling-threshold has no role check (O12).
- (ix) admin-data-import upserts arbitrary tables (O15).
- (x) manage-session `update` writes status directly (S1) with no canceled_* metadata.
- (xi) refreshCancelledTuition runs AFTER the cancel is written; if it throws the lesson stays cancelled and the API reports failure (S2 l.133-143).

## E. Possible "evidence the class was held" (from src/integrations/supabase/types.ts)

- `attendance`: id, session_id, student_id, status, marked_by (string|null), marked_at, notes, created_at, updated_at (types.ts:277). `marked_by` NULL = system/placeholder: auto-mark-attendance (marked_by null, `marked_at` set), repair-attendance (null, notes "Auto-repaired on ..."), the seed trigger, and the Stars sync "seeded placeholders" (supabase/AGENTS.md). A row with marked_by = a user id is a person's mark (mark-attendance sets `marked_by: user.id`, l.156). No explicit "auto-mark" marker column exists. `stars_sync_attendance_state` (event_id, session_id, student_id, status, updated_at; types.ts:4190) marks rows written by the Pixel Pal sync.
- `class_transcripts`: class_id, session_id (nullable), transcript_date, status, raw_text, audio_storage_path, audio_duration_seconds, uploaded_by, title_covered, title_evidence, processing_stage (types.ts:913).
- `lesson_overviews`: class_id, lesson_date, transcript_id, edited_by_teacher, summary, homework (types.ts:2451).
- `homeworks`: class_id, created_by, due_date, submission_type (types.ts:1884) - has no session_id column in the Row shown.
- `point_transactions`: class_id, session_id (nullable), student_id, date, month, points, type, created_by, homework_id (types.ts:3159); `economy_transactions` (types.ts:1354), `student_points` (:4835) not inspected.
- `session_participants`: session_id, participant_type, teacher_id, teaching_assistant_id, attended, absence_note (types.ts:3535) - TA attendance flag.
- `payroll_lines`: month, teacher_id/assistant_id, sessions_count, total_minutes, total_amount_vnd (types.ts:3012) - month-level, derived FROM sessions, so it is a consequence not independent evidence. `payroll_periods` (:3082) exists; types.ts has RPC `payroll_month_is_locked(p_month)` (:6489).
