## 1. The scope decision (1a)

**Decision: the attribute goes on `<html>`, but per ROUTE, from one registry - not app-wide at once.**

`src/lib/ivoryScope.ts` lists the migrated routes (`IVORY_ROUTES`, path + optional `?tab=`). `<IvoryScope>` (in `App.tsx`, inside the router and auth) sets `data-hec-theme="ivory"` on `<html>` while the current route is listed and removes it otherwise, and provides `useIvory()`. The shared primitives (`src/components/ui/**`) and the shell (`Layout`, the student bar, the assistant button) read `useIvory()` and pick between two class sets: the system's, or exactly today's.

Consequences:
- A migrated screen is ivory from the header to its dialogs, popovers, toasts and sheets (they portal under `<body>`, which is under `<html>`), in light and dark. The A4.2 workaround of `data-hec-theme` on each portal content is no longer needed (harmless where it is).
- An un-migrated screen is byte-for-byte today's look: no token is remapped there, no primitive changes class, the old glow and header stay. Nothing ships half old, half new.
- A batch adds its routes to `IVORY_ROUTES` in the same commit that restyles them. When everything is listed, `ROLLOUT_COMPLETE = true` makes it unconditional, the theme default becomes System, and the legacy class sets in `ui/**` are deleted (last batch, R24).

**The experiment** (`docs/evidence/A4.6/exp-*.png`: the attribute forced on `<html>` over four un-migrated screens, light, 375 and 1280, with today's code):
- Token-only screens (teacher dashboard, admin schedule) come out *nearly* acceptable: ivory paper, ink buttons, calm cards - but the coloured icon tiles, glass shadows and sans headings next to ivory surfaces read as unfinished.
- Screens with hard-coded palette classes are clearly half-and-half: the student Homework page shows a blue-to-gold gradient hero and a shimmer title on ivory paper, emoji-coloured nav pills, and the purple assistant button; the parent view keeps its glow.
- 3058 hard-coded palette classes in 254 files remain (inventory, section 3); flipping app-wide would ship all of them clashing at once.

So an app-wide flip is NOT shippable in the interim. A per-screen attribute on each screen root (the A4.2 way) is also rejected: every portal would need it by hand (the A4.2 author had to), the header above the screen would stay old, and the shell would flip mid-page.

**What ships when.** The unit that goes to main is an AREA, not a batch, so a person never walks from an ivory screen into an old one within their own part of the app:
- **Student** area (all `/student/*`, `/tuition`, `/vocabulary`): ships when R01-R07 are merged + R08 (the student flip/review batch). Until then the A4.2 dashboard is the only listed route (as the owner approved it).
- **Staff** area (admin + teacher; they share `/teacher/*` and `/schedule`): ships when R09-R20 are merged + R21 (staff flip).
- **Parent + public** (`/family/dashboard`, `/watch/:token`, `/claim`, `/auth`, `/`): ships with R22 + R23 (parent flip).
- Batches merge to the conductor branch as they pass; an area merges to main in one push with its registry lines. Batches of an area whose flip has not landed are inert on main only if their screens' routes are unlisted AND their class changes are behind `useIvory()` - they are not (they use `hec-*` directly), so **do not push a batch to main before its area's flip**.
- Cross-area components (a file rendered on routes of two areas, e.g. `ScheduleCalendar`, the announcements, `StudentAnalyticsModal` opened from a teacher tool) branch on `useIvory()` until the second area flips; the batch brief says how to spot them.
