# Working alongside other agents without conflicts (owner, 22 Nov 2026; read this first too)
Several sessions and many subagents work in this repo at the same time. Every agent follows these rules.

When a task needs a change in a shared file, one agent, the session lead, makes it; subagents never do.
- **Add, don't overwrite.** Prefer creating a new file next to someone else's over editing theirs (for example a unit's `worksheets.ts` or `football.ts` part instead of editing the unit file). Never delete or rename a file you did not create.
- **Shared files have one writer per session.** These are edited only by the session lead, never by subagents running in parallel: `src/content/lessonDecks/index.ts`, `src/lib/lessonDecks/types.ts`, `scripts/pgtest/run.mjs`, `AGENTS.md`, `package.json` / lockfiles, `src/integrations/supabase/types.ts`. Never write a generic name (`check.mjs`, `out.txt`, `seed.sql`, `/tmp/x`) and never write into a shared tools folder; put temporary files in your own session's scratchpad, never in the repo. Do not reuse or edit another agent's scratch file: copy it under your own name.
- **Migrations:** one new file per change, named `<UTC timestamp>_<topic>.sql`. Before choosing a timestamp, list `supabase/migrations/` on the latest main and pick one later than every existing file, so two sessions never share a timestamp. Never edit a migration that is already on main; add a new one.
- **Claim, then work; report when done.** When a session starts on files another session might touch, tell the other linked sessions which files it owns (SendMessage), and wait for a clash to be settled before editing. When you push, say what you pushed so others can rebase.
- **Rebase before every push** (`git fetch origin main` then rebase), rerun the checks on the combined code, and resolve a conflict by keeping both sides' additions. Never force-push main, and never revert someone else's commit to make yours fit.

# Database migrations
- Migrations under `supabase/migrations/` are the authoritative tree: the owner applies them by pasting into the Supabase SQL editor. A DB change that exists only under `drizzle/migrations/` has not reached that tree.
- So port every new `drizzle/migrations/*.sql` into `supabase/migrations/` as soon as it appears, and point its test at the ported copy. Twice now a guard has been written, tested and committed while being inert: 20261022091000 and 20261027090000. A test that reads its SQL out of `drizzle/` is the tell.
- A new table needs `GRANT SELECT, INSERT, UPDATE, DELETE ... TO authenticated` and `GRANT ALL ... TO service_role` explicitly, because 20260712023825 revoked the defaults on public. Without them PostgREST reports the table as missing from the schema cache, not as forbidden.
- A PARTIAL unique index cannot serve as an `ON CONFLICT` target; PostgREST upserts against one fail with 42P10 at plan time. Use a plain UNIQUE index - NULLs are distinct in one anyway.
- Run the migration regression tests with `node scripts/pgtest/run.mjs` before changing anything under payroll, expenditures or class overhead. They execute the real migration files against an in-process Postgres.

# The register and proof a child was in the room (23 Nov 2026)
- Why: an old `modify_enrollment_transfer` deleted a child's marks in the class they left; a paid August bill was then recalculated to 0 although the teacher had given the child in-class points in those lessons.
- ONE rule says what proves a child was in a lesson: `attendance_proof_rows` (`20261123100000_attendance_proof.sql`). # Tuition pricing: ONE module, and a closed month's bill stands (owner, 23 Nov 2026)
- What a child owes for a month is decided ONLY in `supabase/functions/_lib/tuition-pricing.ts` (`priceStudentMonth`); calculate-tuition and calculate-tuition-bulk call it and price nothing themselves. Do not restate a lesson rule, a percentage or a discount order anywhere else, in TypeScript or in the browser. `tuition-pricing.test.mjs` holds the worked examples.
- The owner's rules: a lesson is billed unless it is cancelled, the child is Excused, or it was given to that child as a free trial (Present, Late, Absent and NO MARK are all billed); the enrollment's custom rate IS the price, higher or lower than the class fee (0 = a free place, not a billable child); discounts in the order that gives away the least: the enrollment's own terms on its class, then fixed amounts, then each percentage on what is left, then the sibling percentage on the winner class's share of what is left; no discount exceeds what it applies to. A discount or bonus counts for a month when it is in force on at least one day of it (`effective_from` BEFORE the next month starts).
- Sibling discount (`compute-sibling-discounts`, `chooseSiblingClass`): off when the family's percent is 0; needs two or more children with something to pay; goes to the ONE class, among all those children's classes, where it costs the school least; decided once a month: an `assigned` state is kept, and only an admin's `reassign: true` picks again, or the family paying as if it were on another child moves it there (see "Free trial lessons and the sibling discount as the family paid"). The screens must read 0 as off (`?? 5`, never `|| 5`).
- `public.tuition_bill_expected` (`20261123150000`) is the same lesson and price rule in SQL, for the hourly bill check. Change one and you change the other in a new migration; `tuition-bill-check.test.mjs` runs both side by side.
- `projected` is the whole month as the timetable stands and is the bill; `actual` is the lessons already held, sent to staff only. The response's `lessons` lists every lesson with its state (billed, excused, cancelled, free = a price of 0, trial = a free trial lesson).
- A CLOSED month (older than `refreshableMonths`: this month, and last month in its first five days) keeps its saved bill: `_lib/past-month-hold.ts`. When today's pricing gives other figures, up or down, both calculators answer the SAVED figures with `held` (`reason: "past_month_changed"`, both sets of figures, a plain sentence) and calculate-tuition writes only the `past_month_differs` flag. When the total is the same and only the base/discount split differs (a custom rate billed the old way, as the class fee less a "Rate Adjustment"), the bill is kept as saved with no flag (`keptAsCharged`). Reports > Checks lists the held bills of every closed month (`ClosedMonthChanges.tsx`, reading calculate-tuition-bulk, which never saves). Only an admin's `force: true` with a `reason` saves the new figures, leaving `past_month_repriced` (who, why, old and new) on the bill; the service role's force is ignored. The one automatic save is `settleToPayment` (service role, sent only by the sibling swap): calculate-tuition honours it only when the new total is exactly the payment recorded on that bill. A frozen bill, a month with no saved bill and the sibling preview are not held. Do not add a way round it: a function that needs a closed month repriced gets `held` and says so (`readRecalc` returns it as its own outcome).
- A held bill says WHY it differs: both calculators answer `held.changes` (`_lib/held-bill-changes.ts`): the saved bill's class lines beside today's pricing, class by class (lessons charged then and billed today with each mark, the lesson price then and today with a custom rate named beside the class fee, the discounts taken off then and today) and `reasons` in sentences. `ClosedMonthChanges.tsx` only renders it ("What changed" on a line). That module prices nothing: today's side is the pricing module's, the charged side is what the bill saved, and what the bill never saved (which lessons were charged, each discount's own amount) is not guessed. A new thing that can move a closed month's figure gets its sentence there and a case in `closed-month-changes.test.mjs`.
- "What changed since you paid": calculate-tuition answers `sincePaid` (`explainPayment` in the pricing module: exact, explained by lessons cancelled or excused since, over, under), and `src/lib/sincePaidLine.ts` words it, English with Vietnamese under it, on the family Tuition page. Families and admins read the same sentence; a difference no lesson explains says so. Do not work the difference out in the browser.
- The calculators read the time from `_lib/clock.ts` so the suites can hold it still (`globalThis.__hecNow`; unset, no month is closed). A new harness that bundles a calculator stubs `clock.ts` like the others, or its cases start failing as their months close.
- `fixtures/tuition-figures.golden.json` was written again on 23 Nov for these rules; the three figures that moved are listed at the top of `invoice-status.test.mjs`.

The lesson is not billed for that child whatever its mark: lesson state `trial` in `_lib/tuition-pricing.ts`, read for both calculators by `_lib/free-trial.ts` (no table yet = none; any other read error fails the calculation), and left out by `tuition_bill_expected` in the same migration. Change one and you change the others; `tuition-bill-check.test.mjs` section 7 runs the calculator beside the SQL. A tick on a closed month prices the month differently, so the bill is held and approved like any other closed-month change.
- A family sometimes puts the sibling discount on another child than the rule chose and pays that way. `siblingFitByPayments` (pricing module) says where the discount must sit for EVERY billable child's recorded payment to equal that child's bill to the dong; when that is another child, `compute-sibling-discounts` with `swapByPayments: true` moves the month's decision there (only the decision it judged), has calculate-tuition save the bills that change (`settleToPayment`) and writes one `audit_log` row (action `sibling_swap_by_payments`). It skips a family whose changing bill is locked. `refresh-month-bills` asks for it every hour for the months it may touch; an older month is checked by an admin in Reports > Checks (`SiblingSwaps.tsx`, dry run first), which also lists every move. Nothing else moves a decided month: do not loosen "to the dong", and do not let a payment that fits nothing move it. `sibling-swap.test.mjs` runs both real functions against each other.

# Frozen bills
- `invoices.tuition_frozen` locks a bill's charged figures (base, discount, total, class breakdown): a trigger keeps them on every update, and calculate-tuition / calculate-tuition-bulk report the saved figures instead of repricing. Used when enrollment history is corrected but what was billed must stand; only an admin explicitly setting it false unfreezes.

# Bill status labels
- `invoices.status` has ONE rule, `paidLabel` in `_lib/invoice-status.ts`: the month's `recorded_payment` against its payable (charge + carry-in debt - carry-in credit). Paid when it covers the payable and the month charged something or received money (nothing left to pay is paid, credit-covered included); partial when anything is recorded; else issued. An admin's `credit` is kept by every writer (`labelAfterPayment`). Every edge function that writes the column uses the helper; the admin screens use its registered mirror `src/lib/invoiceStatus.ts` (never a rule of their own); `ai_action_apply` / `ai_action_undo` use `public.invoice_paid_label` (migration `20261113090000`), compared with the helper by the suite. calculate-tuition re-derives it on each save, writing only when it differs. Never compare cumulative `paid_amount` with one month's charge, and never branch on `status` for money: it is a label, the amount owed is `recorded_payment` and the carry balances.
- Settle Bill is removed (owner, D-23; `settle-bill` is a 410 stub) and so is the calculators' write-off reader (e604b4bf; `scripts/CHECK-writeoff-reader-removal.sql` counted 0 rows it would have counted): no `settlements` row lowers a bill any more, whatever its ledger key. The historical settlements stay ledger-only. `invoice-status.test.mjs` fails if a reader comes back. delete-payment takes the payment off the bill (`recorded_payment`) as well as reversing both ledger legs, and refuses when the bill holds less than the payment put there.
- A signed-in person changes `invoices.recorded_payment` only through `record_admin_payment`: the trigger `a_invoice_recorded_payment_guard` (`20261121090000`) refuses it for `authenticated` / `anon` unless the transaction set `hec.payment_writer`, which only that function does. service_role, SECURITY DEFINER functions and the owner pass. A new writer that runs as the caller needs the flag, and a case in `recorded-payment-guard.test.mjs`; the migration refuses to install while an unknown function writes the column (tuition audit, `docs/TUITION_AUDIT_ROLLOUT.md`).
- Every write of `invoices.recorded_payment` is a compare-and-set on the value the writer read (`_lib/recorded-payment-write.ts`, mirrored as `src/lib/recordedPaymentWrite.ts`): the admin screens report a conflict and reload, the payment functions re-read and try once more. Never write it as "value read + amount" without that condition - two payments on one bill at once lost one that way.
- `ai_action_apply` / `ai_action_undo` as installed are in `docs/sql/ai_action_apply_undo.installed.sql`, last installed by migration `20261117150000` (earlier: 20261113090000 patched them in place). Change them starting from that file and keep `invoice_paid_label`; `ai-actions.test.mjs` fails otherwise. The assistant's payment step records through `record_admin_payment` (payments row + ledger legs + bill in one transaction); its undo reverses it like delete-payment (reversal legs, never a ledger delete) and, for an action that created a child who now has a payment, deactivates the child instead of deleting it. `prevent_direct_payment_deletion` lets `ai_action_undo` delete only the payment its own action recorded. The activity check (`ai_student_activity(uuid, uuid[])`) leaves out the action's own payments, ledger and floor rows and counts a bill a person confirmed or froze.
- calculate-tuition saves the bill on every call, so it must not un-confirm one: a `confirmed` / `adjusted` bill stays so while base, discount and total are unchanged, and goes to `needs_review` with a `changed_after_confirmation` flag (what was confirmed, what it is now) when they change. Only confirm-tuition sets `confirmed`. The lesson-cancellation guard reads both label columns to decide whether a bill is settled.
- calculate-tuition does not write `recorded_payment` (it belongs to the payment paths; writing back the value read at the start overwrote payments made meanwhile) and fails rather than saves when the month's bill or the earlier months cannot be read.
- Both calculators return `carry.payable` from the same helper; a screen should show that, not add it up. A new invoice writer needs a case in `scripts/pgtest/invoice-status.test.mjs`, which also compares every figure with `fixtures/tuition-figures.golden.json` (the function before these changes); regenerate the golden only from figures known to be right.

# Lesson recorder audio: small and short-lived (owner, 24 Nov 2026)
- Why: raw lesson audio (48 kHz FLAC, about 227 MB per lesson hour) filled the free Supabase storage (1.3 GB in five days) and its downloads blew the egress cap.
- Audio is due for deletion 24 h after its lesson-monitor report is saved: `recorder_transcribed_audio_deletable` (`20261124140000`), which `recorder_retention_due` and the `recorder__recording_before_update` trigger both consult. Any new report-like proof goes through that one function. `recorder-retention` removes from Supabase and from R2 and marks a recording deleted only when both listings are empty.
- The recorder captures and stores 16 kHz FLAC (`RECORDER_SAMPLE_RATE`, about 2.8x smaller; numbers and why not lossy in `docs/RECORDER_R2_AND_COMPRESSION.md`). A track keeps one rate; older 48 kHz recordings stay readable. The floor in `recorder_settings.min_bytes_per_sec_flac` went 4000 -> 1500 for it (`20261124150000`).
- The PC job (`scripts/lesson-monitor`) takes each chunk from R2 or Supabase per chunk (`file_objects` row = R2) and never twice in a run; audio already gone is a recorded `refused / audio_gone`. It never deletes on the server.
- The recorder bucket moves to R2 (owner, 27 Nov 2026). `20261127090000_recorder_audio_in_r2.sql` makes `recorder_confirm_chunk`, the complete and deleted transitions, the before-delete trigger and `recorder_import_finish` accept a `file_objects` row as well as `storage.objects` (one rule: `recorder__object_size` / `_present` / `_has_objects_under`; `recorder-audio-in-r2.test.mjs`), and the Worker re-signs a write whose PUT died (its own row, same size and type, no object: `hec-files-worker.test.mjs`). `class-recorder-audio` goes into `R2_BUCKETS` only once that migration is live: before it, every chunk is refused.
- The lesson monitor runs on an Oracle Always Free ARM VM (`scripts/lesson-monitor/server/README.md`): `nightly.py --watch --remote` transcribes with Groq `whisper-large-v3` + Cloudflare `whisper-large-v3-turbo` (`providers/`), reconciles them word by word and re-checks disagreements locally at beam 5 (`providers/reconcile.py`); per piece it falls back Groq+CF -> Groq -> CF -> local. Consent (`lesson_monitor_may_continue`) is asked fresh before EVERY upload; audio is on a tmpfs; secrets are systemd encrypted credentials; it signs in as a separate admin login, never the service role. The class report is requested once the lesson's class work has been read (`classwork.py`: upload window = lesson end + 30 min, OCR `processing` waited for up to 20 min) and rebuilt while unapproved when more is read; the teacher's bell says "Lesson report ready to review" (`20261127100000`). The laptop path (no `--remote`) is unchanged.
- Other private buckets (`class-recordings`, `homework-videos`, `lesson-resources`) still call `supabase.storage` directly; `docs/R2_MOVE_REMAINING_BUCKETS.md` lists every call and the 5-minute-link problem for parent video pages.
