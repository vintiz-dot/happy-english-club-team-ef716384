# Database migrations
- Migrations under `supabase/migrations/` are the authoritative tree: the owner applies them by pasting into the Supabase SQL editor. A DB change that exists only under `drizzle/migrations/` has not reached that tree.
- So port every new `drizzle/migrations/*.sql` into `supabase/migrations/` as soon as it appears, and point its test at the ported copy. Twice now a guard has been written, tested and committed while being inert: 20261022091000 and 20261027090000. A test that reads its SQL out of `drizzle/` is the tell.
- A new table needs `GRANT SELECT, INSERT, UPDATE, DELETE ... TO authenticated` and `GRANT ALL ... TO service_role` explicitly, because 20260712023825 revoked the defaults on public. Without them PostgREST reports the table as missing from the schema cache, not as forbidden.
- A PARTIAL unique index cannot serve as an `ON CONFLICT` target; PostgREST upserts against one fail with 42P10 at plan time. Use a plain UNIQUE index - NULLs are distinct in one anyway.
- Run the migration regression tests with `node scripts/pgtest/run.mjs` before changing anything under payroll, expenditures or class overhead. They execute the real migration files against an in-process Postgres.

# Bill status labels
- `invoices.status` has ONE rule, `paidLabel` in `_lib/invoice-status.ts`: the month's `recorded_payment` against its payable (charge + carry-in debt - carry-in credit). Paid when it covers the payable and the month charged something or received money (nothing left to pay is paid, credit-covered included); partial when anything is recorded; else issued. An admin's `credit` is kept by every writer (`labelAfterPayment`). Every edge function that writes the column uses the helper; the admin screens use its registered mirror `src/lib/invoiceStatus.ts` (never a rule of their own); `ai_action_apply` / `ai_action_undo` use `public.invoice_paid_label` (migration `20261113090000`), compared with the helper by the suite. calculate-tuition re-derives it on each save, writing only when it differs. Never compare cumulative `paid_amount` with one month's charge, and never branch on `status` for money: it is a label, the amount owed is `recorded_payment` and the carry balances.
- Settle Bill is removed (owner, D-23; `settle-bill` is a 410 stub) and so is the calculators' write-off reader (e604b4bf; `scripts/CHECK-writeoff-reader-removal.sql` counted 0 rows it would have counted): no `settlements` row lowers a bill any more, whatever its ledger key. - A signed-in person changes `invoices.recorded_payment` only through `record_admin_payment`: the trigger `a_invoice_recorded_payment_guard` (`20261121090000`) refuses it for `authenticated` / `anon` unless the transaction set `hec.payment_writer`, which only that function does. service_role, SECURITY DEFINER functions and the owner pass. - Every write of `invoices.recorded_payment` is a compare-and-set on the value the writer read (`_lib/recorded-payment-write.ts`, mirrored as `src/lib/recordedPaymentWrite.ts`): the admin screens report a conflict and reload, the payment functions re-read and try once more. Never write it as "value read + amount" without that condition - two payments on one bill at once lost one that way.
- `ai_action_apply` / `ai_action_undo` as installed are in `docs/sql/ai_action_apply_undo.installed.sql`, last installed by migration `20261117150000` (earlier: 20261113090000 patched them in place). The assistant's payment step records through `record_admin_payment` (payments row + ledger legs + bill in one transaction); its undo reverses it like delete-payment (reversal legs, never a ledger delete) and, for an action that created a child who now has a payment, deactivates the child instead of deleting it. `prevent_direct_payment_deletion` lets `ai_action_undo` delete only the payment its own action recorded. The activity check (`ai_student_activity(uuid, uuid[])`) leaves out the action's own payments, ledger and floor rows and counts a bill a person confirmed or froze.

# File storage (R2 move, Nov 2026)
- Supabase Storage is capped at the free 1 GB, so the big buckets are moving to the private Cloudflare R2 bucket `hec-files`, one bucket at a time. Who may read, write or delete a file stays ONE rule: `file_access_can(bucket, path, op)` (`20261118090000`) evaluates the storage.objects policies as installed, as the caller. Change a storage policy and R2 follows; never write a second copy of a bucket's rules in a Worker or in TypeScript. `file_objects` is R2's twin of storage.objects (owner, size, type); `file-store-access.test.mjs` holds the evaluator to Storage's own answers.
- Photos are shrunk in the browser before upload with `src/lib/shrinkPhoto.ts` (2000 px long edge, JPEG 0.82; anything else passes through untouched). A new photo upload uses it. `scripts/shrink-stored-photos.mjs` does the same to stored photos in every bucket, in Supabase AND R2, in place and in the same format (JPEG, PNG lossless, WebP), dry run by default, originals backed up on the PC that runs it; `shrink-stored.test.mjs` runs it against the real Worker code.
- The `hec-files` Worker (`hec-files/worker`, deployed by hand with `npm run deploy` there) signs 5-minute links after asking the database AS THE CALLER (`file_access_can_many`, `file_objects` insert/delete); it holds no service key and decides nothing itself. The app goes through `src/lib/files.ts` (`files.signedUrls / upload / download / remove`); `R2_BUCKETS` there is the one switch per bucket, and a file not copied yet falls back to Supabase. Uploads through the Worker are capped at 100 MB (free plan). `hec-files-worker.test.mjs` and `file-store-client.test.mjs` run the real Worker code.
- A bucket moves with `scripts/copy-bucket-to-r2.mjs <bucket>`: dry run by default, `--apply` copies (R2 first, then the `file_objects` row, so a row means copied; reruns skip and finish), `--remove-from-supabase` deletes a Supabase copy only after the R2 copy reads back byte-identical. Files over 100 MB stay on Supabase. `copy-bucket.test.mjs` runs it against the real Worker code.
- Edge functions reach these files through `supabase/functions/_lib/file-store.ts` (`downloadFile`, `moveFile`): a `file_objects` row means the file is in R2, none means Supabase, so there is no second bucket list. They call the Worker with their own service key and `x-hec-as: service`, which the Worker has the database confirm. `edge-file-store.test.mjs` runs it against the real Worker code.

# Lesson decks (Flipbooks > Lesson Decks)
